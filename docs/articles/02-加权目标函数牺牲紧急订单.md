# 加权目标函数会「理性地」牺牲紧急订单：优先级排产的正确建模

> 关键词：排产、优先级、加权目标、硬约束、CP-SAT
> 项目背景：排产模块要给不同优先级的订单排程。本文复盘我从「加权目标函数」到「硬约束 + 自动降级」的转变，以及一个反直觉的发现。

---

## 0. 问题

排产时，订单有优先级（紧急/高/中/低）。怎么让求解器「优先照顾紧急订单」？

## 1. 第一反应：加权目标函数

最自然的做法是给每个订单一个权重，目标函数最小化「加权延期」：

```
min Σ 权重[订单] × 延期量[订单]
```

紧急订单权重 100，低优先级权重 0.1，看起来没问题。

## 2. 反例：加权和会「理性地」牺牲紧急订单

加权和是**可补偿（compensatory）目标函数**：低优先级订单的延期惩罚加总起来，可以压过紧急订单的小幅延期，于是求解器「理性地」选择牺牲紧急订单。

具体反例：

- 紧急订单 A（权重 100），20 个中优先级订单（权重各 1）。
- 方案一：A 准时，20 个中优先级各延期 2 小时 → 惩罚 = 0 + 20×2 = **40**。
- 方案二：A 延期 0.3 小时，20 个中优先级全准时 → 惩罚 = 100×0.3 + 0 = **30**。

求解器会选方案二——**数学上正确，业务上不可接受**。紧急订单 A 被牺牲了，只因为它延期「只有 0.3 小时」。

## 3. 本质：什么该写进目标函数，什么该写成约束

这个问题暴露了一个建模原则：

> **语义上「必须完成」的 → 写成硬约束；只有「可以权衡」的 → 才放进目标函数。**

紧急订单的交期是「必须完成」，不该让它和「低优先级少延期一点」做交易。所以应该把紧急订单交期写成硬约束：

```
Add(end[紧急订单] <= 交期)
```

## 4. 硬约束的副作用：不可行怎么办

硬约束的问题：如果紧急订单确实赶不上（比如设备坏了、物料短缺），模型直接不可行，求解器返回「无解」。

**不能就此打住。** 正确的做法是**自动降级 + 报警**：

1. 先尝试带硬约束求解；
2. 不可行时，把紧急订单的硬约束降级为软约束（或报告具体缺口）；
3. 明确告诉计划员：「紧急订单 A 最早可于 X 完成，缺口 Y 小时」，并给出选项（加班 / 外协 / 拒单）。

这是工业 APS 的 ATP（可承诺量）/ 可达性检查的标准做法。

## 5. 兜底：无论如何都要报「不可行在哪」

不管是硬约束冲突，还是某道工序没有可用设备，**系统必须明确报出是哪个订单、哪道工序、缺什么资源**，而不是转圈、超时或返回一个空计划。

「算不出来」本身是合理结果，但「算不出来还不说为什么」就是 bug。

## 6. 总结

| 做法 | 问题 | 结论 |
|---|---|---|
| 加权目标函数 | 可补偿，会牺牲紧急订单 | 只用于「可权衡」的目标 |
| 硬约束 | 可能不可行 | 用于「必须完成」的目标 |
| 硬约束 + 自动降级 + 报警 | 无 | 正确做法 |

**核心一句话：优先级是「约束」，不是「权重」。** 这句话我在这个项目里反复跟自己和队友强调——因为直觉总是把我们往「加权」上带。
